# 在线合同智能审查与修订系统需求文档

版本：V1.0（需求评审稿）  
日期：2026-10-15  
项目定位：面向内部业务、法务人员的合同审查与在线复核平台  
核心方案：AI 审查 + 在线文档编辑器 + Word 原生修订与批注

## 1. 项目背景

用户希望在浏览器中完成合同上传、审查、修改、复核和导出，并能将结果交给使用 Office/WPS 的人员继续处理。

当前通过网页预览、文本替换和双栏 Diff 模拟修订的方式存在以下问题：

- 正文编辑、条款编辑、意见处理和导出状态相互影响，容易出现覆盖与版本不一致。
- 段落变化被整块高亮，用户难以分辨实际修改与未变文字。
- 同一条款的不同风险拆成多张卡片，缺少统一修改方案。
- 修改过程与 Word 原生修订脱节，网页状态不能自然延续到办公软件。
- 模型异常被规则回退掩盖，造成重复意见、固定评分或“审查成功但没有改写”。
- 审查等待过程不透明，长日志和遮罩影响阅读、取消及后续操作。

新项目以 DOCX 文档及其原生修订为核心，网页 Diff 仅作为辅助对照能力。

## 2. 产品目标与边界

### 2.1 产品目标

1. 用户在一份在线合同中直接编辑、查看修订、添加批注及接受或拒绝修改。
2. AI 根据真实合同、我方立场和审查条件，生成可定位的意见及针对性修订。
3. AI 建议自动写入待复核的建议版本，保留修订痕迹，不自动替用户确认采纳。
4. 网页展示、复核状态、保存版本与导出文件保持一致。
5. 审查失败、重试、保存和版本变化均有明确反馈，不把规则结果冒充模型审查。

### 2.2 首期范围

- DOCX 合同上传、在线阅读与编辑。
- AI 全文审查、按条款合并意见、自动生成修订和批注。
- 单份文档的原生修订展示、接受、拒绝和人工修改。
- 审查概览、意见定位、处理备注、针对意见追问。
- 审查任务、文档版本、刷新恢复与下载。
- 模型配置、最大重试次数和公开分析摘要。
- 单人复核为主，多标签页编辑冲突保护。

### 2.3 暂不纳入首期

- PDF 扫描件 OCR 与在 PDF 上进行 Word 式原生修订。
- 自动电子签章、合同履约、付款和归档审批系统。
- 自行研发完整 Office 排版与协同编辑内核。
- 无依据的合同健康评分、法律效力保证或自动批准签署。
- 完整多人协同流程、复杂组织审批及历史系统全量迁移。

## 3. 用户角色

| 角色 | 主要操作 |
| --- | --- |
| 业务人员 | 上传合同、补充背景、发起审查、查看意见、调整正文、导出 |
| 复核人员 | 核对 AI 依据、接受或拒绝修订、人工修改、添加备注、完成复核 |
| 管理员 | 配置模型服务、文档服务、访问权限和运行参数 |

首期允许同一用户兼任业务与复核人员，但需要保留实际操作人及时间。

## 4. 核心业务流程

1. 新建任务，上传 DOCX，系统保存不可覆盖的原始版本。
2. 打开合同工作区，默认展示原始文档；用户可先编辑并保存。
3. 选择我方立场，补充背景、关注事项及谈判尺度。
4. 点击“开始审查”，先提交在线编辑器中尚未保存的内容，确认保存成功后创建本次审查快照。
5. 后台执行审查，实时展示执行状态和模型公开分析摘要。
6. 按实际条款合并风险，为每个问题组生成统一修改方案。
7. 在审查快照的副本中写入原生修订与批注，生成 AI 建议版本。
8. 用户在同一份建议版本中复核、接受或拒绝修改，必要时继续人工修订。
9. 保存最新版本并完成复核，下载带修订稿、清洁稿或审查意见书。
10. 如需再次审查，以已保存的当前版本创建新快照，历史审查和版本继续保留。

任一步骤失败时，不得覆盖原始文件或上一版已保存成果。

## 5. 页面与交互

### 5.1 任务入口

首页或任务列表提供“新建审查”、历史任务及最近操作记录。合同工作区不重复放置“新建审查”入口。

任务列表至少展示合同名称、审查状态、复核进度、更新时间及操作人。未计算评分的任务不展示虚构分数。

### 5.2 合同工作区

采用“左侧概览 + 中间文档 + 右侧意见”的结构：

- 左侧审查概览、右侧审查意见默认展开，可使用边界把手收起或展开。
- 中间默认是一份在线文档，审查后打开带原生修订的建议版本。
- 双栏对照作为可选视图，不作为必须经过的页面。
- 侧栏收起后释放空间，由在线编辑器重新适配可用宽度，不沿用旧预览器强制 80%/100% 的计算方式。
- 不使用遮挡文档的浮动侧栏；小屏幕可切换面板，仍须保证编辑器和处理按钮可用。

顶部保留合同名称和必要操作：审查设置、开始/重新审查、保存、导出、完成复核。审查立场使用下拉选择，不平铺多个按钮。

### 5.3 审查概览

展示风险分布、问题组数量、处理进度、审查版本和结果来源。专项检查与审查过程可按需展开。

相同风险不同时以多份长文本重复铺满概览和意见栏。风险数量以问题组统计，并可额外标注其包含的风险点数量。

首期不提供健康分。未来增加评分时，必须另行定义评分依据、适用范围及验证方案。

### 5.4 审查意见与修订清单

每张卡片对应一个实际条款或连续且相关的原文范围，内容包括：

- 条款标题、风险级别及处理状态。
- 该条款存在的多个风险点及各自影响。
- 可核验的原文引用、依据和统一修改方案。
- 关联修订数量、接受/拒绝、编辑、待复核、重置、备注与追问入口。

点击意见定位到文档中对应的修订或批注；点击关联修订时可回到对应意见。

常用操作保持可见，长篇依据、原文全文、对照和备注按需展开。不得为了压缩界面而隐藏所有核心风险说明。

搜索与风险、处理状态筛选集中呈现。按钮不因侧栏宽度变化而遮挡或出现无意义的空白。

### 5.5 在线文档与修订展示

- 默认显示修订标记，插入、删除、格式变化由编辑器原生呈现。
- 未改动内容不铺红底；风险定位与实际文字修改采用不同视觉语义。
- 支持按编辑器能力切换修订标记、原文及最终效果视图；视图切换不得隐式接受修订。
- 支持人工编辑、批注、撤销与重做。人工修改应记录实际作者，AI 修改使用明确的 AI 作者标识。
- 缩放采用紧凑统一控件，优先复用编辑器原生能力。
- 常见合同中的表格、编号、页眉页脚、分页、签章图片及字体设置应尽量保留，并通过实际样本验收。

## 6. AI 审查与自动改写

### 6.1 审查输入与结果真实性

审查输入由已保存的文档快照、合同类型、我方立场、背景、关注事项和谈判尺度组成。

深度审查必须成功调用模型，不得在失败后静默替换成固定规则结果。若提供规则检查，应作为独立且明确标识的模式。

每项意见应包括实际条款位置、原文依据、风险说明、修改方向及可执行修订；无法定位的意见必须标明定位失败，不能替换其他相似段落。

### 6.2 意见合并

- 同一条款中的多个审查角度合并为一个问题组，保留各风险点。
- 不仅依据标题相同就合并，须验证实际原文范围。
- 同一问题组提供统一改写，避免多个替换建议重叠或互相覆盖。
- 一个问题组可以关联多处原生修订和批注，不要求一条意见只能对应一次插入或删除。
- 不同条款的问题保持独立；跨条款依赖应明确关联。

### 6.3 改写规则

1. 在满足风险处理目标的前提下进行最小必要修改，保留无关内容。
2. 不擅自改变已有主体、金额、税率、日期、期限和责任归属。
3. 不把其他合同的示例条款、税率或金额套入当前合同。
4. 保留原有空白，不批量新增“待确认”字段、主体信息表单或证照清单。
5. 需要业务确认的信息应放在审查意见或批注中；缺少事实导致无法安全改写时，保留原文并说明原因。
6. 事实完整性提示不应自动扩大成整段重写。
7. 生成内容须校验原文唯一匹配、范围冲突、条款覆盖、重复项及是否真正发生必要修改。

### 6.4 写入建议版本

- 自动生成建议版本，不需要用户逐条点击才看见 AI 修订。
- AI 插入和删除以原生修订写入，风险说明以关联批注或平台意见呈现。
- 自动写入建议不等于自动采纳；新生成意见默认待处理。
- 若某条款未生成有效修订，明确显示失败或仅提供意见，不把原文显示为“改写成功”。
- AI 生成期间不得直接覆盖用户正在编辑的文档；发布建议版本前须验证基线仍适用，发生变化时提示重新生成或进入冲突处理。

### 6.5 失败反馈与重试

- 默认最大重试 3 次，不包含首次请求，即单次模型操作最多请求 4 次。
- 重试次数可配置；审查和统一改写分别受各自次数上限约束。
- JSON 无效、字段缺失、改写遗漏、重复或新增不必要占位符时，将校验错误反馈给模型修正，不仅重复同一提示词。
- 网络异常、临时限流和服务端异常采用有上限的退避重试。
- 未配置模型、鉴权失败、无效模型/接口地址等不可恢复错误直接提示。
- 取消或达到整次任务时限后，不得继续重试、发布结果或覆盖已保存版本。
- 首期沿用单次流式响应 120 秒、整次审查等待 6 分钟的默认上限；整体时限优先于剩余重试次数，部署时可配置。

## 7. 过程透明与等待体验

展示公开、可核验的处理信息，不展示模型内部思维链，也不编造模拟思考日志。

用户应能看到：

- 正在读取和审查的版本、条款范围与阶段。
- 当前模型请求轮次、重试原因及剩余次数。
- 流式返回的完整初步意见：原文引用、风险说明、修改方向。
- 格式、原文匹配、冲突及改写校验结果。
- 已生成修订数量、未能处理的条款与原因。

初步意见必须标记“待校验”，不得提前写成最终已采纳结果。重试后区分各轮结果，主界面优先显示当前有效轮次。

进度窗口须限制在视口内，标题和取消按钮固定可见，中间内容滚动。执行日志默认收起，不把整篇合同输出成日志。等待期间定期更新状态，不伪造百分比；真正完成前不得达到 100%。

允许收起进度窗口继续阅读；正在生成结果的版本应有清晰的编辑保护。重新打开可恢复查看当前任务进度。

## 8. 修订复核与状态一致性

### 8.1 原生修订与业务状态

原生修订状态和平台复核状态相互关联，但不简单等同。用户“不采纳”是复核决定，拒绝关联原生修订是文档操作，两者需要以可恢复的事务流程保持一致。

| 业务状态 | 规则 |
| --- | --- |
| 待处理 | 新生成的问题组，关联修订尚未全部作出决定 |
| 待复核 | 用户明确标记需要进一步确认，不自动修改正文 |
| 已采纳 | 对应修订全部接受且编辑器保存成功；无自动修订的意见由用户明确确认处理 |
| 不采纳 | 用户拒绝建议，关联修订拒绝并保存成功，保留决定与理由 |
| 部分处理 | 同一问题组部分修订已接受或拒绝，其余仍待处理 |
| 已手工处理 | 用户通过人工修改处理问题，并明确确认完成 |

用户在编辑器中直接接受或拒绝修订时，平台也应更新关联状态。不得只改变右侧标签而不改变文档，或只改变文档而仍显示旧状态。

### 8.2 重置与撤销

原生修订被接受后，其原始标记可能消失，因此不能把“重置”设计为仅修改状态字段。

- 未落盘的操作可使用编辑器撤销能力。
- 已保存的操作通过保留的基线、修订映射及操作记录恢复到新版本，不覆盖其他人工修改。
- 无法无冲突恢复时，明确提示并提供历史版本查看或恢复入口。

修订标识、直接操作事件和恢复能力须在接入验证阶段确认，不得假定编辑器天然提供全部双向联动接口。

### 8.3 完成复核

存在待处理、待复核、部分处理、保存未完成或修订冲突时，不允许直接完成复核，并说明阻塞事项。

完成复核需要保存成功、记录实际版本及操作人。完成后如继续修改，创建新版本并重新标记需要复核。

## 9. 保存、版本与刷新恢复

至少保存以下版本：上传原件、审查基线、AI 建议版本、用户保存版本及完成复核版本。

- 文档文件、审查结果、意见分组、修订映射及处理记录由后端持久化。
- localStorage 仅保存缩放、面板状态等偏好，不作为合同和结果的唯一存储。
- 文件必须在保存回调确认后才标记保存成功；浏览器中的编辑状态不等于已落盘。
- 回调需验证文档键、版本和任务归属，支持重复通知的幂等处理。
- 旧回调不得覆盖新版本；多标签页编辑须有会话、锁或版本冲突保护。
- 刷新后恢复正确文档、审查版本、修订状态与意见，不重新发起模型调用。
- 多次审查相互隔离，失败的新审查不覆盖上一版结果。
- 切换任务、离开页面或重新审查时，提示并处理尚未保存的编辑。

## 10. 导出

| 导出类型 | 内容与约束 |
| --- | --- |
| 带修订稿 DOCX | 导出当前已保存版本，保留尚未接受的修订、批注及作者信息 |
| 清洁稿 DOCX | 在副本上计算最终文本，可预览确认；不隐式改变工作版本或采纳状态 |
| 审查意见书 | 包括审查版本、条款问题、依据、建议及处理记录，标明模型与人工内容 |

存在未决意见时，导出本身不应被强制阻止，但应明确导出的是哪一版、是否包含待处理内容。不得要求必须重新审查才能下载已有保存文件。

在 Office/WPS 中打开导出文件后，须验证文字、排版、修订与批注可继续使用；不宣称所有复杂文档百分之百兼容。

## 11. 技术与部署方案

### 11.1 系统组成

| 模块 | 职责 |
| --- | --- |
| 前端 | Vue 3 + Vite + TypeScript；承载任务、概览、意见和编辑器容器，不自行实现 Office 排版内核 |
| 业务后端 | 沿用 Python/FastAPI 技术方向，管理任务、权限、审查编排、文件、版本与保存回调 |
| 文档服务 | 优先验证 ONLYOFFICE Docs，负责在线编辑、原生修订、批注与编辑会话 |
| AI 服务 | 按统一接口调用模型，负责结构化意见、条款改写和公开分析摘要 |
| 数据与文件 | 数据库保存结构化记录，文件存储保存不可变文档版本；生产环境配置备份 |
| 后台任务 | 审查独立执行，具备取消、超时、重试和事件订阅能力；浏览器断线不应自动丢失任务 |

前端至少拆分任务列表、合同工作区、在线编辑器、审查概览、意见卡片、过程面板及模型设置组件。文件版本与业务状态集中管理，禁止多个组件各自维护一份正文。

### 11.2 开发与生产部署

开发环境可在本机通过 Docker 启动文档服务，前后端单独启动。浏览器、文档服务及后端必须能互相访问所需接口；容器内 localhost 不代表宿主机。

首期生产环境可在同一台服务器部署反向代理、业务后端、文档服务及存储，分别以独立服务或容器运行。容量增长后可拆分文档服务与后台任务。

文档服务负责编辑和回传，不替代业务系统的版本记录与持久存储。文件传输采用受控下载接口，编辑器通过保存回调将结果交回后端。

### 11.3 接入前必须验证的能力

1. 部署版本、授权及接口能否满足编辑、修订、批注和自动化控制要求。
2. AI 生成的 DOCX 原生修订能否被编辑器、Office/WPS 正确识别。
3. 平台意见与原生修订、批注的稳定关联方式。
4. 在编辑器中直接接受、拒绝及人工修改后，能否可靠同步业务状态。
5. 保存、强制保存、关闭会话、异常退出和重复回调的行为。
6. 保存后修订标识是否变化，如何重新定位与处理冲突。
7. 实际合同中表格、编号、页眉页脚、分页及签章图片的兼容情况。

若某项能力需要商业版或插件，应先明确成本与实现路径，再确定首期交付范围，不以“嵌入编辑器”代替完整接入验证。

## 12. 核心数据对象与接口能力

核心对象：用户、合同任务、文档版本、编辑会话、审查任务、条款锚点、问题组、风险点、修订关联、批注关联、处理记录、执行事件及导出记录。

每个审查任务绑定不可变输入版本；每个问题组绑定该审查任务及源文范围；每项修订关联文档版本、操作作者及对应问题组。文档版本应记录父版本、文件标识、内容校验值和保存来源。

接口至少支持：

- 上传与受控读取文件、创建和列出文档版本。
- 创建编辑会话、生成编辑器配置、接收和验证保存回调。
- 发起、取消、查询审查任务，订阅事件并在断线后恢复读取。
- 查询问题组、修订关联，提交复核决定、备注和追问。
- 确认版本冲突、完成复核和创建导出任务。

接口实现方式可调整，但必须携带任务、版本及幂等标识，防止重试导致重复修订或覆盖。

## 13. 权限与数据保护

- 用户只能读取和修改授权范围内的合同、版本和意见。
- 模型密钥由后端安全管理，不写入文档、批注、日志或导出文件。
- 模型调用前明确合同实际发送到的服务，不在未授权情况下传给额外服务。
- 文档服务访问文件与保存回调需要身份验证；外部文件下载地址须受限制，防止任意地址下载。
- 合同及附件按待分析数据处理，不执行其中的指令。
- 记录用户操作、模型调用结果及版本变化，日志避免保存密钥或无必要的合同全文。
- 删除、保留期限、备份恢复策略在部署时明确。

## 14. 验收标准

| 编号 | 场景 | 验收要求 |
| --- | --- | --- |
| A01 | 上传合同 | 原始 DOCX 不被覆盖，可在线打开，常见排版元素通过样本验收 |
| A02 | 原生在线修订 | 人工插入、删除保留修订记录，可在编辑器接受或拒绝 |
| A03 | AI 自动修订 | 审查完成后生成带修订建议版本，不需要逐项点击生成，不自动确认采纳 |
| A04 | 同条款多风险 | 合并为一个问题组，风险点完整，统一方案不互相覆盖 |
| A05 | 高亮准确 | “30 日”改为“60 日”只显示实际增删，相同内容不整段标红 |
| A06 | 缺失事实 | 原文主体和账号为空时，不新增整套待确认表单，不虚构事实 |
| A07 | 编辑互不覆盖 | 人工修改其他条款后，再处理 AI 建议，不丢失既有修改 |
| A08 | 双向状态 | 从侧栏与编辑器两种入口接受或拒绝，都能对应正确文档和复核状态 |
| A09 | 重试上限 | 默认首次请求加最多 3 次重试；格式错误反馈修正，鉴权错误不重复请求 |
| A10 | 真实性 | 模型不可用时明确失败，不生成固定分数和模板意见冒充成功 |
| A11 | 过程透明 | 最终结果前可收到初步公开分析；清晰标注待校验，不输出内部思维链 |
| A12 | 取消与超时 | 操作始终可见，取消后不发布新结果，不覆盖既有文档，达到时限停止等待 |
| A13 | 弹窗布局 | 长日志和较小视口下窗口不超出屏幕，标题和取消可见，滚动正常 |
| A14 | 刷新恢复 | 恢复当前保存版本、修订、意见和处理记录，不重复调用模型 |
| A15 | 回调冲突 | 重复及过期保存回调不重复创建修订、不覆盖新版本 |
| A16 | 再次审查 | 先保存编辑，再绑定新快照；旧审查记录可查且不被污染 |
| A17 | Office/WPS 衔接 | 导出的样本在目标软件中能继续查看并处理修订、批注 |
| A18 | 清洁稿导出 | 导出副本，不静默接受工作版本中的全部修订 |
| A19 | 完成复核 | 未决意见、部分处理、冲突和未保存情况均阻止误完成并明确原因 |

样本文档至少覆盖短合同、长合同、表格合同、编号条款、多段替换、重复条款、已有修订、已有批注及签章图片。验收应包括浏览器操作和导出文件的实际打开验证。

## 15. 分阶段交付

### 阶段一：编辑器接入验证

验证原生修订、批注、保存回调、意见定位、双向状态同步及实际文档兼容性，输出可行性结论与授权成本。

### 阶段二：单人业务闭环

完成上传、编辑、AI 审查、分组改写、建议版本、逐项复核、保存、刷新恢复及三类导出。

### 阶段三：稳定性与体验

完成失败反馈重试、任务恢复、取消超时、版本冲突、过程透明、布局优化及回归样本库。

### 后续扩展

在首期闭环稳定后，再评估多人协同、企业规则库、审批流程、PDF/OCR、合同知识库和更多编辑服务适配。

## 16. 待评审事项

- 文档编辑服务最终选型、授权版本、部署资源与费用。
- Office/WPS 的目标版本及首期兼容样本范围。
- 原生修订映射、双向处理同步与已保存操作重置的可行性。
- 首期账号体系、合同访问边界与部署网络条件。
- 模型服务、数据发送范围、任务容量和输出长度限制。
- 是否迁移旧项目合同及审查记录；旧 Diff 结果如何标识和转换，禁止直接冒充原生修订记录。
