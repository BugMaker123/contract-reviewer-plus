# 01 架构与目录

## 1. 技术基线与运行边界

| 层 | 技术方向 | 边界 |
| --- | --- | --- |
| 前端 | Vue 3、Vite、TypeScript、Pinia | 单页应用，路由级加载，按业务模块组织 |
| API | Python、FastAPI、Pydantic | 鉴权、协议转换、调用用例，不直接执行长任务 |
| 数据 | PostgreSQL、SQLAlchemy、Alembic | 结构化数据、事务、版本与迁移 |
| 文件 | 本地存储起步，对象存储适配接口 | 保存不可变 DOCX，不把大文件写入数据库字段 |
| 后台执行 | 独立 Worker、Redis 队列，首期采用成熟任务队列实现 | 数据库保存任务事实；队列只负责通知，不作为唯一记录 |
| 文档服务 | 首选验证 ONLYOFFICE Docs | 独立部署，通过服务端接口与前端 SDK 适配 |
| AI | OpenAI 兼容协议适配器起步 | 厂商 SDK、流式格式与错误转换留在适配层 |
| 事件 | SSE + 持久事件表 | 支持重连；事件传输与任务执行分离 |

不在首期拆成大量微服务。业务 API 与 Worker 可以复用同一代码包，但作为独立进程运行。可靠后台审查不依赖一次 HTTP 请求或进程内临时任务的生命周期。

FastAPI 官方将进程内 BackgroundTasks 与适合独立执行的较重任务作了区分：[后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)。本项目选择独立 Worker 是为任务恢复与取消提供基础。

## 2. 依赖方向

`HTTP / Worker 入口 → application 用例 → domain 规则与 ports 接口`

`infrastructure 适配器 → ports 接口`

`bootstrap 组装 → application + infrastructure`

约束：

- domain 不导入 FastAPI、ORM、编辑器 SDK、模型 SDK。
- application 不直接调用外部 SDK、访问浏览器或拼接 SQL。
- HTTP 路由不直接更新 ORM 对象后绕开用例。
- 模块之间通过公开用例或窄接口协作，不跨模块导入内部仓储实现。
- 确实跨模块的业务编排放在 `workflows/`；单模块规则仍留在模块内部。
- 依赖注入只在 bootstrap 完成，不通过全局可变对象获取数据库或客户端。

## 3. 目标目录

```text
apps/
  web/
    src/
      app/                 # 路由、依赖组装、启动与主题
      pages/               # 页面组合，不实现核心业务规则
      features/
        contracts/         # 任务列表、上传与合同元信息
        editor/            # 编辑器会话、能力与事件适配
        review/            # 发起审查、过程订阅与结果
        issues/            # 问题组、筛选、备注、追问
        revisions/         # 修订命令、决定状态与映射视图
        versions/          # 保存状态、版本历史、冲突提示
        exports/           # 导出任务及下载
        settings/          # 模型与工作区偏好
      shared/
        ui/                # 真正业务无关的基础组件
        http/              # 网络客户端与错误转换
        events/            # SSE 传输与重连
        types/generated/   # 从契约生成；不手工改
        styles/            # 设计变量和基础样式
  api/
    src/contract_app/
      bootstrap/           # 配置、依赖与应用工厂
      http/                # 路由与 HTTP schema
      worker/              # 队列入口与任务调度
      modules/
        contracts/
        documents/
        reviews/
        issues/
        revisions/
        exports/
        identity/
      workflows/           # 跨模块业务编排
      infrastructure/
        persistence/
        storage/
        editors/
        models/
        queue/
        events/
      shared/              # ID、时钟、通用错误等少量基础类型
tests/
  unit/
  integration/
  contracts/
  e2e/
  fixtures/
docs/
  技术设计/
  adr/
tools/
  quality/                 # 大小、依赖、契约门禁
deploy/                    # 容器、代理、环境模板
```

各后端业务模块按需包含 `domain/`、`application/`、`ports/`。没有内容的层不提前创建空文件；每个模块必须有精简 `README.md` 说明公开入口。

## 4. 拆分示例：reviews 模块

```text
reviews/
  domain/
    review_run.py
    review_state.py
    retry_policy.py
  application/
    start_review.py
    cancel_review.py
    run_pipeline.py
    steps/
      prepare_snapshot.py
      build_context.py
      analyze_clauses.py
      validate_findings.py
      consolidate_issues.py
      compose_revisions.py
      publish_result.py
  ports/
    model_gateway.py
    task_repository.py
    event_publisher.py
  README.md
```

`run_pipeline.py` 只编排步骤、检查截止时间与取消信号，不内嵌提示词、JSON 解析、DOCX 修改和数据库实现。

## 5. 可扩展点与克制

- 编辑器、模型、文件存储与任务队列使用 ports，因为存在明确外部依赖变化。
- 领域规则使用具体函数或对象，不为每个函数创建接口。
- 首期不设计通用插件市场、动态模块加载、可视化工作流平台或万能仓储。
- 编辑器差异通过 capability 声明，不在业务层散落 `if provider == ...`。
- 第二个真实调用场景出现后再提炼共享组件，禁止把一次性代码全部放进 shared。
