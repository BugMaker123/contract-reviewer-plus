# 07 可维护性与文件门禁

这是实施约束，不是建议清单。新项目必须先落地自动门禁，再继续扩展功能。当前交付为设计文档，下面列出的工具需在脚手架阶段实现。

## 1. 文件大小硬限制

按物理行数统计，包含注释和空行；同时限制字节，防止把整段代码压成一行绕过门禁。

| 文件 | 建议目标 | 硬上限 | 字节上限 |
| --- | --- | --- | --- |
| Vue SFC | 100–200 行 | 300 行 | 24 KiB |
| TS/JS 业务文件 | 100–200 行 | 300 行 | 24 KiB |
| Python 业务文件 | 150–250 行 | 400 行 | 32 KiB |
| 手写 CSS | 100–200 行 | 300 行 | 24 KiB |
| 单个测试文件 | 150–300 行 | 500 行 | 40 KiB |
| 单份提示词 | 40–80 行 | 120 行 | 16 KiB |
| 专题设计文档 | 100–180 行 | 250 行 | 32 KiB |
| 模块 README | 30–60 行 | 80 行 | 12 KiB |
| ADR | 40–70 行 | 100 行 | 16 KiB |

HTML 入口只保留应用挂载、元信息和构建入口，不允许重新嵌入整页业务脚本或样式。

以下文件排除于手写文件门禁：锁文件、厂商静态库、自动生成 API 类型、构建产物。排除必须使用精确目录或文件规则；业务文件不能伪装为 generated。生成文件按业务拆分并标注生成来源，不要求开发者整份读取。

## 2. 达到阈值后的动作

- 到硬上限的 80% 发预警，新功能优先放入合适的新模块。
- 超过任一硬上限：CI 失败，禁止合并。
- 行数减少但职责、依赖和重复代码增加，仍不通过设计评审。
- 禁止删注释、压缩代码、拼接巨型字符串或随意外提常量来规避阈值。
- 长函数目标不超过 40 行；超过 80 行需拆分或附具体例外说明。
- 单文件高分支复杂度、过多业务依赖、过多公开方法属于额外拆分信号，不等达到行数上限。

例外只允许具体文件，必须记录原因、责任人、拆分计划和到期日。新项目不允许为手写核心业务文件长期豁免。

## 3. 拆分必须形成职责边界

不合格：`workbench1.ts`、`workbench2.ts`、`helpers.ts`、`misc.py`、`service_all.py`。

合格拆分示例：

| 大文件原本混合的职责 | 拆分目标 |
| --- | --- |
| 模型调用、JSON 提取、校验、重试、摘要投影 | transport、parser、validator、retry_policy、public_projection |
| 编辑器挂载、保存、命令、事件与销毁 | session、save_bridge、commands、events、lifecycle |
| 意见展示、筛选、备注、追问 | IssueCard、IssueFilters、IssueComment、IssueFollowup |
| DOCX 遍历、文本定位、修订写入、批注、检查 | extraction、anchors、revision_writer、comments、validation |
| HTTP、用例、SQL、队列投递 | router、application command、repository、outbox dispatcher |

禁止只是把同一闭包中的全局状态拆到多个文件，并继续互相任意读写。每次拆分说明输入、输出、状态所有者和依赖方向。

## 4. 复用标准

- 两个真实场景共享稳定行为时再提炼复用，不因代码相似就强行建通用框架。
- 共用业务规则放 domain/application，共用无业务 UI 放 shared/ui。
- SDK 差异留在 adapters，调用方依赖领域能力而不是厂商对象。
- 一个函数只提供有意义的参数，避免几十个布尔开关控制不同业务。
- 不建立全项目可访问的 `GlobalContext`，用例显式声明少量依赖。
- 重试、错误、事件格式和版本校验只有一个权威实现，禁止每个模块复制一份。
- 接口 schema、领域对象、数据库模型各司其职，不强求一种类型穿透全部层。

## 5. 依赖门禁

前端：

- `shared → feature` 禁止。
- `feature A → feature B 内部目录` 禁止；确需调用仅通过公开入口。
- 页面可组合 features，feature 不导入 pages。
- SDK 只能出现在对应 adapter 目录。

后端：

- domain 不依赖 framework、ORM、SDK。
- application 依赖 domain/ports，不依赖 infrastructure。
- 其他模块不能导入本模块的内部仓储和 ORM 模型。
- 禁止循环依赖；依赖反向时通过事件或重新明确模块归属解决。

门禁使用 AST/import 分析，不仅靠字符串搜索。import 例外必须可审计。

## 6. 模块说明文件

每个业务模块 README 必须包含：

1. 一句话职责、负责的状态和明确不负责的内容。
2. 公开入口及关键类型。
3. 允许依赖与不允许依赖的模块。
4. 两三个关键不变量。
5. 对应测试和常用验证命令。
6. 修改该模块时优先阅读的文件清单。

README 不复制源代码或完整全局文档。接口变化时同步更新入口说明，避免上下文文档过期。

## 7. 面向 AI 编码的工作方式

每个任务形成一个简短上下文清单：

```text
目标：修改什么可观察行为
不变量：必须保留什么业务语义
阅读：相关专题 → 模块 README → 公开接口 → 目标实现
修改：具体模块和预计文件
验证：相关测试、构建与门禁
结果：完成项、未完成项、证据与风险
```

- 先读索引定位，不每次加载完整 PRD、全部技术文档和整个工作台源码。
- 一个变更尽量只涉及一个明确用例；跨模块变更按契约、实现、接入分步骤。
- 接近上下文预算时写简短交接，保留决策、已改文件、验证结果和下一步，不复制整段工具输出。
- 不能为了节省上下文省略关键调用链；发现理解需要读取几十个文件时，先检查模块耦合和文档缺失。
- 功能实现不写进巨型“万能入口文件”；修复时同步检查是否触发拆分阈值。
- 代码行数上限保障局部可读性；运行时模型长合同上下文另按 [05](05-AI与上下文.md) 管理。

## 8. CI 必须落地的检查

| 检查 | 失败条件 |
| --- | --- |
| file-limits | 手写文件超行数/字节上限、例外过期 |
| architecture | 依赖越界、循环引用、SDK 泄漏到领域层 |
| formatting/lint | 代码格式、危险模式、未使用依赖 |
| typecheck/schema | 类型错误、生成契约未同步 |
| production-build | 前端构建失败、缺失样式或资源 |
| unit/contract | 相关规则、状态机、协议与适配器验证失败 |
| integration/e2e | 保存、复核、恢复等关键场景失败 |
| doc-links | 技术索引或模块文档存在断链 |

计划工具位置为 `tools/quality/check_file_limits.py` 和依赖检查配置。阈值集中配置，CI 输出“路径、实际值、上限、对应规则”，不只输出 failed。

门禁先在新项目目录全量执行。旧项目迁移期间只对明确列出的旧文件设临时基线，禁止继续增加其体积；不能用“历史原因”豁免整个 backend 或 frontend。

## 9. PR 与代码评审

PR 必须回答：业务变化、状态归属、影响的契约、是否新增复用、文件大小、验证证据。

拒绝以下情况：巨型组件、万能 store、万能 service、无界事件缓存、无界重试、把全文当全局状态反复复制，以及用 mock 成功掩盖真实编辑器或模型未接通。

实施完成标准包含门禁已运行且成功，不是“文档里写过应该拆分”。
