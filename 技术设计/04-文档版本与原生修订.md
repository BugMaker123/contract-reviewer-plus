# 04 文档版本与原生修订

## 1. 版本模型

`DocumentVersion` 是不可变文件快照，至少记录：

- `version_id`、`document_id`、`parent_version_id`。
- 文件对象键、内容 hash、创建人和创建来源。
- `kind`：original、user_saved、review_baseline、ai_proposal、verified。
- `review_run_id`、对应编辑会话与创建时间。

一个合同维护当前工作 head 和最近成功审查指针。两者是不同概念，人工保存可以使当前工作版本领先于审查版本。

不得复用旧文件对象键覆盖历史内容。清洁稿是导出副本，不改变工作 head 的修订状态。

## 2. 文件发布与存储

1. 写入临时对象，核对 DOCX 可读性、大小与内容 hash。
2. 将对象置为不可变可寻址产物。
3. 在数据库事务内创建版本元数据，并对 head 做 compare-and-swap。
4. 事务失败时不发布 head，临时或孤立对象由清理任务处理。

对象存储和数据库之间没有天然分布式事务，不能把“文件写出”直接等同“版本发布成功”。

## 3. 编辑会话与保存

每个 `EditorSession` 绑定基线版本、用户、编辑器、会话文档键及会话 generation。多人编辑同一工作副本使用同一受控会话策略，不能每次页面渲染随意更换文档键。

建议流程：

1. 后端签发受限编辑会话配置。
2. 编辑器加载文档，前端记录 ready/dirty 状态。
3. “保存/重新审查/导出”触发 `flush`，创建 `save_request_id`。
4. 文档服务回调，后端验证会话与 generation，受控下载文件并校验。
5. 新建不可变版本，推进会话检查点，完成保存请求。
6. 前端收到 `document.saved` 后才显示保存成功，后续命令携带新版本。

回调必须幂等。迟到回调可以作为历史分支保留，但不能回退当前 head。

不同回调状态、文档键生命周期及保存行为须按选定版本验证，不能把任意回调当成完整保存。参考：[ONLYOFFICE 保存回调](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler)。

## 4. 修订计划与编辑器隔离

AI 不直接操作编辑器 SDK，输出平台自己的 `RevisionPlan`：

```text
plan_id, review_run_id, base_version_id
operations[]:
  operation_id, issue_group_id, kind
  anchor, expected_source_hash
  expected_text, replacement_text
  author, public_reason
```

`kind` 首期支持明确的 insert、delete、replace 和 comment；不支持的格式修订不得静默改成删除整段重建。

文档适配层将计划转换为 DOCX 原生修订或已验证的编辑器命令。生成前校验原文，生成后提取文档再次核对目标结果与未修改区域。

若实现原生 OOXML 写入，应独立拆分段落遍历、run 切分、修订节点生成、批注写入与验证。不得让模型直接生成可执行 XML 或任意编辑器脚本。

## 5. 稳定锚点

锚点组合使用版本、结构位置、前后文、引用文本与指纹，必要时使用经验证的书签或内容控件。不得仅依赖段落序号、标题或一次字符串 replace。

重复条款、表格、合并单元格、跨 run、软换行均需专门样本验证。不能唯一定位时返回 `ANCHOR_AMBIGUOUS`，保留原文。

插入标记或内容控件是否影响排版、是否被编辑器保存保留，必须验证，不作为未经证明的稳定 ID 方案。

## 6. 业务 ID 与厂商 ID

平台维护稳定的 `operation_id`、`binding_id`，映射到特定版本下的编辑器修订/批注引用。

厂商引用可能在保存后改变。映射至少包含 `document_version_id`、provider 引用、锚点和内容指纹；版本变化后重新验证。

一张意见卡可关联多个修订。不得把一张卡的状态直接映射为一个编辑器按钮状态。

## 7. 接受与拒绝的可恢复命令

命令状态：`requested → executing → awaiting_save → confirmed`，异常进入 failed 或 needs_reconciliation。

1. 用户发命令，携带 command_id、expected_version 与 operation_ids。
2. 后端校验权限和版本，登记操作意图。
3. 编辑器适配器执行命令，返回结果回执，不立即确认“已采纳”。
4. 等待保存检查点，验证目标修订的最终效果。
5. 更新映射及业务复核状态，命令进入 confirmed。

编辑器中直接操作也需转换为同类业务事件并对账。如果 SDK 无法完整提供通知，应在保存后检查文档差异与标记，明确延迟同步状态；未经验证不能承诺实时双向一致。

无法识别原生接受动作和人工改写时，标记需要用户确认，不自动推断已采纳。

## 8. 重置、撤销与冲突

- 编辑器未保存操作通过其撤销能力处理。
- 已保存决定不简单回写状态；根据原计划、操作记录和当前版本创建恢复命令。
- 当前目标已被其他修改影响时，不覆盖；返回冲突及相关版本。
- 首期不实现任意复杂内容自动三方合并。可提供查看历史、重新应用计划或在新分支恢复的明确选择。
- 恢复历史版本应创建新 head，不删除当前历史。

## 9. 再审查与人工编辑

审查输入永远绑定已保存快照。AI 生成期间允许用户继续阅读；若允许继续编辑，应在发布时比较 head。

head 未变化可发布到工作版本；已变化则发布为待合并建议分支并提示冲突，不静默覆盖。首期可限制审查期间当前会话编辑以降低复杂度，但必须明确提示并允许取消。

## 10. 导出一致性

- 导出请求绑定已保存版本，不能混用后来的意见和旧文件。
- 带修订稿保留尚未接受的修订与批注。
- 清洁稿在副本上按已声明的预览策略生成，并注明是否包含未决建议。
- 导出完成不改变复核状态。
- Office/WPS 与在线编辑器的兼容性用样本验证，不凭 XML 合法就认定展示正确。

## 11. 能力闸门

ONLYOFFICE 的外部自动化接口涉及具体授权版本，官方列明 Automation API 属于 Docs Developer：[接口说明](https://api.onlyoffice.com/docs/docs-api/usage-api/automation-api)。

阶段一必须验证定位、修订命令、保存确认和直接操作同步。不能以“编辑器支持审阅”推导“我们需要的全部接口均免费可用”。
